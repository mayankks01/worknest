# Foundation decisions

- React + TypeScript + Vite provide the web client. Local API requests use Vite's proxy; pilot deployment will need a same-origin reverse proxy serving the compiled assets.
- Django 5.2 LTS + Django REST Framework form the modular backend. PostgreSQL is the only configured database. Redis supports Celery; organization writes now capture an audit event and durable outbox row in the same transaction.
- Python 3.12 is the baseline. Django and DRF compatibility were checked against their official release documentation: https://docs.djangoproject.com/en/5.2/releases/5.2/ and https://www.django-rest-framework.org/community/3.16-announcement/. Vite's Node requirement was checked at https://vite.dev/guide/.
- `/api/v1/health/live/` measures process availability only. `/api/v1/health/ready/` checks PostgreSQL and Redis with bounded timeouts and returns 503 on failure. Neither endpoint reports internal connection strings. Worker/email/storage checks must be expanded when those integrations become application dependencies.
- Default REST permissions require Django session authentication. Health routes are public; global account endpoints have explicit access rules and CSRF protection on every POST. See `ACCOUNTS.md`. Secure cookie/HTTPS defaults are disabled only by explicit local debug configuration; production proxy settings require a separate deployment review.
- Database ownership and application use are separate. Step 4 adds forced RLS, trusted actor/organization transaction context, membership discovery, and adversarial checks under a non-owner role. Exactly one active Owner is enforced by a deferred composite FK plus a partial unique index. See `ORGANIZATIONS.md` for the policy boundary and controlled discovery exception.
- Step 3 introduced the custom UUID identity before applying Django auth/session migrations. User and account-token tables are global. Account tokens also hold durable email delivery state, recovered by Celery beat. Organization creation retry records are actor-scoped global records; tenant audit/outbox rows require organization context.
- The React UI follows the user-supplied navy/blue mockup. Account screens call the same-origin API. Dashboard fixtures remain isolated at `/preview`; they never represent authenticated organization data. See `UI-DESIGN.md` for the visual reference.
- This Compose file is a local development configuration. It is not a production deployment or security baseline. External provider credentials, hosting region, scanning service, and operating budget remain future decisions.
- Local object storage uses RustFS 1.0.1, following its official Docker configuration: https://docs.rustfs.com/en/installation/container/docker/. The S3 bootstrap uses boto3 and rejects unexpected bucket policies. The pilot provider is still undecided.

- Step 5 adds invitations, per-organization member usage, scoped retry records, live team authorization and transactional ownership transfer. Invitation email uses leased outbox jobs with beat recovery and bounded retries. Narrow fixed-search-path database helpers support forced RLS without recursive policy queries. See `TEAM.md`.

- Step 6 adds private projects, explicit project memberships, versioned task CRUD, quota accounting and offboarding cleanup. Four new tables force organization-level RLS with composite relationship constraints. Shared service policies enforce project visibility; the usage row serializes capacity/access changes, while task versions prevent lost updates. Board/list views and the scoped dashboard use real API data. See `PROJECTS.md`.

- Step 7 adds comments, private attachments and storage reservations. Fourteen tenant tables now force RLS. File workers use an exact organization/file capability and recheck the uploader's live project access. Private S3 and ClamAV I/O run outside business transactions, and leased jobs recover missed dispatches. Content hashes, format parsing, scanner results and a second access check protect authenticated downloads. Cleanup releases quota only after confirmed object deletion. See `COLLABORATION.md`; wider reconciliation and lifecycle purge remain Steps 8–9.

- Step 8 adds three forced-RLS tables for notifications, preferences and reconciliation (17 tenant tables total). Transactional outbox consumers create unique inbox records, while separate leased email jobs recheck access and preferences. Owners/Admins can inspect append-only audit history and retry failed work. A durable five-minute reconciliation schedule corrects usage and scans old orphan objects outside database transactions. See `NOTIFICATIONS.md`; retention and lifecycle purge remain Step 9.

- Step 9 adds forced-RLS export and maintenance tables (19 tenant tables total), scoped search, private ZIP exports and scheduled deletion. Exact-job background capabilities separate retention/purge from ordinary user access. Storage I/O happens outside business transactions; leases and live authorization guard export publication and download. A non-identifying maintenance receipt survives organization purge. See `LIFECYCLE.md`.
